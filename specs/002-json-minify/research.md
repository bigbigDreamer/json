# Research: JSON 一键压缩

## Decision 1: 复用现有清理与解析链路，在 `lib/json-tools.ts` 中新增独立压缩入口

- **Decision**: 保留现有 `formatJsonInput` 作为格式化入口，新增一个独立的压缩入口，二者共享底层“清理隐形字符 -> 解析 -> 规范化 JSON 值”的纯逻辑，但不引入参数化工厂式入口。
- **Rationale**: 当前项目已经把 JSON 清理、解析和树视图数据准备集中在 `lib/json-tools.ts`。压缩功能与格式化功能的前置校验完全一致，复用底层安全链路可以避免重复实现；同时保留独立入口函数能让调用点语义清晰，避免把多种行为揉进一个难读的高阶函数。
- **Alternatives considered**:
  - 在组件内直接调用 `JSON.stringify(data)` 生成压缩结果：被否决，因为会把转换逻辑散落到 UI 层，违反现有项目的逻辑分层原则。
  - 用一个带 `mode` 参数的通用工厂函数同时处理格式化和压缩：被否决，因为虽然复用更多，但会降低调用方可读性，也不符合当前项目偏好的显式函数设计。

## Decision 2: 压缩结果作为独立结果态展示，不覆盖原始输入，也不替代现有树视图

- **Decision**: 在现有工作台中新增明确的“压缩 JSON”触发操作，并让压缩结果以独立结果态被查看和复制；源输入保持原样，现有格式化结果与树视图保留。
- **Rationale**: 规格已明确要求不覆盖原始输入，同时 `speckit.constitution` 把结构浏览能力定义为核心产品价值。如果压缩动作直接替换输入或替换树视图，会损害用户的定位、对比与复制体验。
- **Alternatives considered**:
  - 点击后直接把输入框内容改成压缩 JSON：被否决，因为用户容易失去原始上下文，且不利于继续编辑。
  - 让压缩结果完全取代现有输出区：被否决，因为会削弱项目的结构化浏览主能力。

## Decision 3: 自动化测试以纯函数单元测试为主，优先覆盖安全边界

- **Decision**: 为 `lib/json-tools.ts` 增加 Vitest 单元测试，覆盖合法 JSON 压缩、基础类型、已压缩输入、隐形字符清理和非法输入错误反馈等边界。
- **Rationale**: 当前仓库尚未形成成熟测试基线，而该功能最关键的风险在于“是否错误改变 JSON 语义”。纯函数测试最直接、稳定，也最符合 `speckit.constitution` 对 sanitization、parsing 和 copy-related formatting helpers 的高优先级测试要求。
- **Alternatives considered**:
  - 仅依赖手工浏览器验证：被否决，因为无法为语义安全提供稳定回归保障。
  - 直接引入完整端到端测试：暂不优先，因为本次功能主要变更点在纯转换逻辑，先补高价值单元测试更高效。

## Decision 4: UI 契约围绕“操作可辨认、结果可复制、失败可解释”组织

- **Decision**: 把本功能的交互契约定义为三段式流程：触发压缩、确认当前结果处于压缩态、复制完整压缩文本；任何解析失败都必须阻止结果输出并给出可理解说明。
- **Rationale**: 这与规格中的 P1-P3 用户故事完全对齐，也符合现有产品“状态清晰、复制高效、失败明确”的原则。
- **Alternatives considered**:
  - 只提供压缩按钮，不补充结果态识别：被否决，因为用户难以确认当前复制的是格式化结果还是压缩结果。
  - 沿用现有错误态但不区分压缩操作来源：被否决，因为会降低问题定位效率。
